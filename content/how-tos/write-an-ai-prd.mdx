*A practical guide for junior intermediate and senior product managers*

A product requirements document (PRD) describes a user problem, the outcome the team wants to achieve, and the behavior the team agrees to deliver. For a feature that uses artificial intelligence (AI), it also defines what the system can rely on, what it should do when evidence is missing, and how the team will judge whether the feature is ready to launch.

Imagine you are building a recruiter evidence brief. A recruiter opens a CV, compares it with a role’s hiring criteria, and writes a first review note. The proposed feature finds relevant passages and drafts the note. The recruiter checks the evidence and decides what to save. We’ll use this example to turn a product idea into a PRD.

## Use this guide at your level

| Experience level | What to practice |
| --- | --- |
| Junior PM | Write the problem statement, map the user journey, draft a user story, and turn one requirement into Given, When, Then acceptance criteria. |
| Intermediate PM | Translate discovery into MVP scope. Define edge cases, instrument the workflow, design an evaluation set, and plan the pilot. |
| Senior PM | Challenge the investment case, decide which risks and trade-offs are acceptable, and agree on the launch gates, owners, and rollback plan. |

## What you will build

1. A problem statement grounded in discovery and a measurable baseline.

2. An MVP scope and a product hypothesis that connect the feature to a user outcome.

3. A user flow and a set of functional, AI behavior, and non-functional requirements.

4. An evaluation plan, an experiment, and a release decision with named owners.

5. A PRD you can share with design, engineering, QA, data, and operations.

## How the PRD fits with other product documents

A roadmap shows the sequence of outcomes or bets the team plans to pursue. A PRD specifies a particular feature. A technical design explains how the system will implement it. The backlog breaks the work into items the team can deliver. Link these documents so readers can move from a product decision to its implementation and tests.

The recruiter example, baseline, and thresholds in this guide are illustrative. Set your own targets after measuring the current workflow, estimating feasibility, and reviewing risk.

## Discover the Problem Before Defining the Feature

### Identify the user and their job

Start with product discovery, the work of finding out which problems matter and where the current experience falls short. Use interviews to understand why people struggle, observation to see what they actually do, and analytics to estimate frequency. In the PRD, distinguish evidence from assumptions and assign an owner to validate important unknowns.

A target segment is the group you are designing for first. A persona describes a representative user and their context. A Jobs to Be Done (JTBD) statement captures the progress that person wants to make in a situation. A user story translates one part of that job into a product capability the team can design and test.

| Product term | Recruiter example |
| --- | --- |
| Target segment | Recruiters reviewing applications for technical roles using a shared hiring rubric. |
| JTBD | When I review a technical application, I want to locate verifiable evidence for each role criterion so I can write a review another recruiter can understand. |
| Problem statement | Recruiters switch between CVs and role criteria while writing notes. Relevant passages can be hard to locate, and a reviewer may have to reopen the CV to verify a note. |
| User story | As a recruiter, I want each draft evidence item to link to its source so I can verify it before saving my review. |

### Establish the baseline and outcome

A baseline is a measurement of the current experience. For this example, time the existing workflow from opening an eligible application to saving the first review note. Capture completion and abandonment alongside time. Separate role and CV types if their complexity differs. Write down how you measured, when, and across how many cases.

An outcome is a change for the user or business. A feature is a capability delivered to help produce that change. Here, shipping the draft button is an output of the team’s work. Reducing first-review time while maintaining evidence quality is the intended outcome.

**Example product hypothesis.** If eligible recruiters can review a draft with links to CV evidence, median time to save a first review will fall from an illustrative eight minutes to six in the pilot, while completion and evidence quality meet the agreed guardrails.

**Senior review.** Estimate how many reviews are eligible, how often recruiters face this problem, and whether the time saved justifies build, inference, review, and support costs. Specify what evidence would make the team stop investing.

## Prioritize Scope and Choose the AI Approach

### Compare ways to solve the problem

A structured rubric could reduce time spent formatting notes. Keyword search could surface exact terms in a CV. An AI model could help identify varied descriptions of the same skill and draft a short evidence note. Test the smallest combination that addresses the observed bottleneck. Record the alternatives considered, the rationale for the chosen approach, and the assumptions that still need testing.

A proof of concept tests a specific feasibility question, such as whether the system can locate a sentence in a parsed CV. A prototype helps test the interaction, such as whether recruiters can understand a draft and open its citations. A minimum viable product (MVP) is the smallest usable version that lets you test the product hypothesis with real users.

### Define the MVP and its boundaries

| Priority | Example scope and rationale |
| --- | --- |
| Must have | Generate on request using one authorized English-language, text-readable CV and an approved role rubric. Show evidence status and source links. Support editing, manual review, and explicit save. |
| Should have | Let the recruiter flag individual evidence items. Include this in the pilot if feedback can be reviewed and routed without delaying the core workflow. |
| Later | Support scanned documents, additional languages, and other application sources after evaluating each new input type. |
| Outside the pilot | Candidate scoring, ranking, automatic rejection, application-stage changes, and candidate messaging. |

### Use prioritization to explain the decision

MoSCoW groups work into Must have, Should have, Could have, and Won’t have for this release. RICE compares candidate investments using reach, impact, confidence, and effort. Either can make trade-offs visible. Mandatory controls and dependencies still need to be satisfied even when their direct reach appears small.

**Dependency.** A prerequisite the team needs to deliver the feature. Here, the document parser must preserve stable source locations before the product can show working citations.

**Assumption.** Something the plan currently treats as true. Here, recruiters can open linked passages quickly enough for verification to fit their workflow.

**Constraint.** A limit the solution must respect. Here, a draft can draw evidence only from the authorized CV attached to the current application.

**Senior review.** Agree on the scope of model authority before estimating the work. In this example, the model proposes text. The application enforces permissions and valid states. The recruiter reviews and saves the result.

## Write the User Flow and Requirements

### Map the main path and recovery paths

A user journey describes the user’s experience across the broader task. A user flow describes the steps and branches in a particular interaction. For the evidence brief, the main path is to open the application, request a draft, inspect the source, edit the note, and save. Specify the loading state and what the recruiter can do while generation runs.

Document the edge cases with equal care. A readable CV with no relevant evidence gets “Evidence not found.” A CV that mentions the skill without proving the required duration gets “Needs review.” An unreadable file or timed-out request offers manual review. A change to the CV or rubric marks the draft stale and requires regeneration or manual review before saving a current note.

### Separate three types of requirements

**Functional requirements.** Describe what users or the system can do. For example, open a cited passage, edit the draft, or save the note.

**AI behavior requirements.** Describe the sources, output fields, acceptable responses, and when to abstain. For each criterion, return a status and cite the exact supporting passage when evidence is found. An abstention is a deliberate response when available information cannot support a conclusion.

**Non-functional requirements.** Describe how well the feature must operate. Specify performance, reliability, accessibility, security, and cost. For example, make the brief and source links keyboard-accessible and return a usable draft within the agreed time at expected load.

### Make acceptance criteria observable

Acceptance criteria are conditions a requirement must satisfy. Given describes the starting state. When describes the trigger. Then describes the expected behavior. Add the expected recovery path when relevant.

| ID and priority | Acceptance criteria |
| --- | --- |
| R1 · Must · Check access | Given a recruiter cannot access a CV, when they request a draft for it, then generation is blocked and no CV content is returned. |
| R2 · Must · Handle uncertainty | Given a CV mentions Django but provides no duration, when the brief assesses a two-year Django criterion, then it shows “Needs review,” cites the mention, and leaves duration unspecified. |
| R3 · Must · Preserve control | Given a recruiter edits the draft, when they select Save, then their edited note is saved once and the application stage stays the same. |
| R4 · Must · Offer a fallback | Given no usable draft is returned within 20 seconds, when the request times out, then the UI explains what happened and keeps manual review available. |

Tie each requirement ID to its design, test, and release evidence. This traceability helps the team see what needs to change when a requirement changes.

## Define Data Inputs and AI Behavior

### Write an input and output contract

Define which inputs are accepted, who can supply or access them, and how current they must be. In the example, the input is one authorized, text-readable English CV and the current approved rubric. Engineering and product must agree on file limits, parsing failures, source identifiers, and how versions are checked at save time.

Define each output field and its allowed values. A brief item has a criterion ID, evidence status, optional excerpt and source location, and a draft note. The status can be “Evidence found,” “Evidence not found,” or “Needs review.” When the status is “Evidence found,” the excerpt and location are required. If the system finds ambiguous evidence, it may show an excerpt with “Needs review.”

**Grounding.** Connecting a generated claim to an approved source that supports it. A citation shows where to check. The evaluation must verify that the passage actually supports the claim.

**Hallucination.** Output presented as fact without adequate support. For example, a brief invents “three years of Django” when the CV mentions the skill but gives no duration.

**Human in the loop.** A person reviews or approves a consequential step. Here, recruiters can verify passages, correct or dismiss a draft, and explicitly save a note. Their approval is a separate product action.

### Assign controls to the system

Enforce authorization and workflow permissions in the application. Treat uploaded content as data. Test prompt injection, where text inside a CV tries to change the model’s instructions or obtain unrelated data. In the example, the application restricts retrieval to the current authorized CV and gives the model no access to application-stage controls.

For an agent that can take actions, add an action inventory. For each action, specify permission scope, confirmation, retry behavior, how duplicates are prevented, and whether the result can be undone. Define which actions require human approval.

### Specify data handling and versioning

Map collection, processing, storage, logging, vendor handling, and deletion. Identify the owner for each. Decide what recruiters can see, what analytics can collect, and how access changes apply to saved drafts. Have the appropriate reviewers approve the data flow before pilot exposure.

Record the model, prompt, rubric, and evaluation set versions used in testing. The technical design can document the implementation. The PRD should say which behavior, quality thresholds, and controls must still hold when a version changes.

## Measure Product Value and AI Quality

### Give each metric one clear job

| Metric type | Recruiter example |
| --- | --- |
| Primary KPI | Median active time from opening an eligible application to saving the first review note. Compare AI access with the manual workflow during the same pilot. |
| Adoption and funnel | Track eligible applications opened, draft requested, draft returned, source opened, and review saved. Adoption is applications with a draft request divided by eligible applications opened in the AI group. |
| AI quality | Grounded claim rate is the number of surfaced factual claims supported by their source divided by all surfaced factual claims. Track coverage as answerable criteria correctly supported divided by all answerable criteria. |
| Operational | p95 latency is the time within which 95% of measured successful requests finish. Pair it with usable drafts within the timeout divided by all eligible requests. Track cost per usable draft, including failed calls and retries. |
| Guardrail | A metric that protects against an unacceptable side effect. Track the share of eligible first reviews completed, substantive corrections, and any confirmed unauthorized disclosure or materially fabricated evidence. |

### Build an evaluation plan

An evaluation set is a collection of input cases with expected behaviors or scoring instructions. Start with permitted examples that resemble real usage. Include sparse CVs, varied role criteria, ambiguous dates, and unusual but supported formats. Reserve a held-out set for release evaluation. Keep cases used to tune the feature separate.

Create a scoring rubric with examples of a pass, a minor issue, and a critical failure. Have reviewers independently score a sample and resolve disagreements. Report counts, denominators, and results by relevant input slice. Track correct abstentions on ambiguous cases alongside coverage so a system cannot score well simply by refusing to help.

**Acceptance test.** Given the Django CV with no dates, verify that the feature returns “Needs review.”

**Release gate.** Across the agreed evaluation set, require at least 98% supported claims and 90% coverage on answerable criteria, with zero observed critical failures. These are illustrative thresholds. Record the minimum sample, owner, and response if any threshold is missed.

### Test the product hypothesis in a pilot

Define the eligible population, assignment method, exposure, time window, and decision rule before launch. Where feasible, randomly assign comparable recruiters or applications to AI access or manual review. Choose the assignment unit to limit spillover. Analyze eligible cases by assigned group, including cases where recruiters choose manual review. Compare time among completed reviews and report completion and abandonment so the speed metric is interpretable.

## Make the Release Decision

### Move from evaluation to exposure

| Stage | Evidence and decision |
| --- | --- |
| Offline evaluation | QA and the evaluation owner review held-out results, edge cases, and regressions. Fix and retest any failed release gate before pilot exposure. |
| Internal trial | Engineering checks access controls, telemetry, expected load, manual fallback, and the feature flag. Design verifies that states and controls are usable. |
| Limited pilot | Product and recruiting operations agree on eligibility, duration, comparison groups, and minimum exposure. Monitor review time, completion, quality, and incidents. |
| Expansion | The launch approver reviews outcome and guardrail results, unresolved risks, support readiness, and evidence by cohort. Record the decision to expand, hold, or pause. |

### Write the decision rule before the pilot

**Expand.** In this example, product reviews a two-week pilot after at least 100 eligible reviews per group. Expansion requires a median of six minutes or less in the AI group and at least 25% improvement versus manual review. Before the pilot, agree on the allowed change in completion, the cost ceiling, and how to sample pilot drafts to verify that quality holds. The sample count is an illustrative exposure minimum. Use baseline variability and the decision at stake to size an actual experiment.

**Hold.** If exposure is too low, important slices lack evidence, or quality falls short without a critical incident, keep the rollout limited. Assign a follow-up owner and retest before expansion.

**Pause and recover.** A confirmed critical incident triggers a pause. The on-call owner disables generation using the feature flag, routes pending requests to manual review, and coordinates review of affected drafts. Retest the fix before the launch approver authorizes resumption.

### Assign ownership and record risks

A feature flag lets the team turn functionality on or off for selected cohorts. A rollback restores a previously approved version or behavior. State who can use each control, what happens to pending work, and who checks whether previously generated outputs are affected.

A risk register tracks what could go wrong, the impact, the mitigation, and the owner. For example, if an old draft could be saved against a new rubric, engineering owns version checks and QA owns the stale-draft test. Use a decision log for trade-offs, approvals, and open questions, each with a due date.

**Senior review.** Decide whether the workflow improvement justifies incremental cost, human review time, and ongoing support. Specify which residual risks the launch approver accepts and which trigger a pause.

## Sample PRD for a Recruiter Evidence Brief

*A concise example you can use as a model*

**Owner and decision.** Recruiting Product owns the PRD. Design, Engineering, QA, Data, and Recruiting Operations review it. The decision requested is approval to prepare a limited pilot after the offline gates and data review are complete.

**Problem and baseline.** Technical recruiters switch between a CV and a role rubric to find verifiable evidence for their first review. The example assumes an eight-minute median per completed review. Product and Data will verify the baseline and completion rate before pilot enrollment.

**Hypothesis and scope.** An editable draft with source links will reduce the AI group’s median first-review time to six minutes or less while meeting quality and completion guardrails. V1 supports authorized, text-readable English CVs and approved rubrics. Recruiters make hiring decisions and explicitly save their own notes.

**Core behavior.** The recruiter requests a draft from an application. For every criterion, the draft returns “Evidence found,” “Evidence not found,” or “Needs review.” A supported item links to the exact CV passage. The recruiter can edit, dismiss, or save the note. Generation failure or timeout offers manual review. CV or rubric changes mark an existing draft stale.

**Acceptance criteria.** Given a CV mentions Django without dates, when the recruiter requests a draft for a role requiring two years of Django, then the brief shows “Needs review,” cites the mention, and leaves duration unspecified. An unauthorized request returns no CV content. Saving an edited note does not change the application stage.

**Quality and operations.** QA evaluates held-out CVs and challenge cases. Proposed gates are 98% supported claims, 90% coverage on answerable criteria, and zero observed critical failures. Engineering targets p95 of 12 seconds for successful drafts at pilot load, with at least 95% of eligible requests yielding a usable draft within 20 seconds.

**Pilot and release decision.** Product and Data run a two-week comparison against manual review with an illustrative minimum of 100 eligible reviews per group. Expansion requires at least 25% lower median time and six minutes or less in the AI group, plus the agreed guardrails. A confirmed unauthorized disclosure or materially fabricated evidence triggers a pause and review.

**Open decisions and dependencies.** Before pilot enrollment, Data finalizes the assignment design and completion guardrail. Engineering verifies parser quality and sets a cost ceiling with Product. Privacy and security reviewers approve data handling. Recruiting Operations confirms the pilot cohort and appoints a launch approver.

This summary shows the decisions a PRD needs to capture. Attach the full requirement list, test rubric, data-flow review, and measurement plan for delivery.

### Run a short PRD review

- Ask design to show the main flow and the uncertainty and error states.

- Ask engineering to name which controls the application enforces and show how the manual path works.

- Ask QA and data to connect each critical requirement to a test, metric, or launch gate.

- Ask the launch approver to explain the evidence needed to expand and who can pause the rollout.

## Product and AI Terms at a Glance

| Term | Meaning in a PRD |
| --- | --- |
| JTBD and user story | JTBD describes the progress the user wants in a situation. A user story describes a capability that helps them make that progress. |
| Objective and key result | An objective is a goal. A key result is measurable evidence of progress toward it. A key performance indicator (KPI) is a metric the team tracks to understand performance. |
| Baseline and target | The baseline describes current performance. The target specifies the change the team aims to achieve. |
| Prototype and MVP | A prototype tests an interaction or design idea. An MVP is a usable release designed to test the core product hypothesis. |
| Edge case and fallback | An edge case is an unusual but relevant situation. A fallback is the path offered when the primary flow cannot proceed. |
| Functional and non-functional requirements | Functional requirements describe what the feature does. Non-functional requirements define qualities such as latency, accessibility, and reliability. |
| Acceptance criteria and release gate | Acceptance criteria define expected behavior in a testable scenario. A release gate defines the evidence required before advancing a rollout. |
| Instrumentation and funnel | Instrumentation records product events. A funnel shows how many eligible users or attempts move through successive steps. |
| Guardrail and rollback | A guardrail is a limit on an adverse outcome. A rollback restores a previously approved version or behavior. |
| Grounding and abstention | Grounding ties a claim to supporting evidence. Abstention is the defined response when the system lacks sufficient evidence. |
| Offline evaluation and pilot | Offline evaluation tests the feature on cases outside live use. A pilot gives a limited cohort access to validate the real workflow. |
| LLM and inference | A large language model processes and generates language. Inference is a run of the model to produce a result from an input. |
| Retrieval and RAG | Retrieval selects relevant source material. Retrieval-augmented generation gives selected material to a model as context for its response. |
| Model drift and regression | Drift is a change over time in inputs or observed performance. A regression is a decline in previously verified behavior, often checked after a change. |
